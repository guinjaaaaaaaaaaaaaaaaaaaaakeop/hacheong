The artifact is a plan document: Markdown, one `## <Q-id> …` section per question the goal must answer (ids named after the question — `Q-store`, `Q-currency` — never a bare number), each section stating what will be built and **acceptance sentences** a check can decide, `## slices` last (one per line, naming the question ids it closes). When the project runs mangsang, a section is a projection of a named concept and says so in its first line. The plan is a **contract**: the sentences in it are what a builder will be held to and what a test will be written against, so a sentence that no check could ever decide ("user-friendly", "fast", "robust") is not an acceptance sentence but a wish, and a sentence that two readers can read two ways is a decision not yet made. Evidence in this domain is the sentence itself, quoted — there is no exit code; a plan claim is decided by a person's reading, and what a member can do is make that reading precise. The request the plan answers (a REQUEST.md, a goal sentence) is the source; the plan may not promise what the request did not ask, nor drop what it did.

## dakdol

Write or amend exactly the sections the request names, from the source the brief points at (the request, the questions). Each section: the concept it projects (when there is a net — read `mangsang concept list` and name one; propose a new concept in `decisions` rather than inventing a section with no owner), what will be built, and acceptance sentences — each one a sentence a test could decide, with the observable it decides on (an exit code, an output line, a file's content, a stored key). Do not write code, tests or README. A behavior the request left open is a `decision`, listed, not a sentence written as if it were asked. `verified`: the shape check you ran, if the runner names one (`chongdae` checks `plan/document@1`); otherwise say so in `non-claims`. Touch nothing but the plan (and `plan/questions.json` when the brief says so).

## sibi

You read the plan sections and the request they answer. `undecided`: a sentence that leaves two readings, or a case (empty input, the boundary, the second call, the error path) the section is silent on that a builder would have to settle. `contradiction`: two sentences — in one section, across sections, or between a section and the request — that cannot both be true. `unchecked`: an acceptance sentence with no observable in it (nothing an exit code, an output or a file could decide), or a section with no acceptance sentence at all. Quote the sentence. The request's `checks` list is about code, not plans — it is empty here by design; an empty `checks` is never a finding in this domain. A promise the request did not make is `contradiction` with the request, quoted from both.

## teujip

In this domain your tests are **counter-examples**: for each acceptance sentence, the concrete input and observable that would falsify it, written as a test that a builder must make pass (`test_<Q-id>_<case>`) — you write them from the plan alone, as the code's future adversary, and they must fail now (nothing is built yet, or the sentence is new). A sentence you cannot turn into a test is not testable: quote it in `non-claims` — that is a finding for the plan, not a test to skip. Touch only test files.

## chojja

You are the stakeholder who wrote the goal and now reads the plan for the first time. You have the request (or the goal sentence) and the plan; you do not read code, tests or run records. `did-not-work`: the plan promises something the request did not ask, or drops something it did (quote both). `unclear`: a section you, the person who asked, cannot tell whether it gives you what you meant (quote the sentence). `surprise`: a decision the plan made on your behalf that you would have wanted to be asked about. You do not fix or suggest; an empty answer means the plan reads as the request meant.
